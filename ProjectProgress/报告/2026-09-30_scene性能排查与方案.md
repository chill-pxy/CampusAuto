# scene 关卡性能排查与优化方案（仅诊断，未实施修复）

**日期：** 2026-09-30，Asia/Shanghai

- **关卡：** `/Game/Campus/Maps/scene`
- **引擎：** UE 5.8.2
- **硬件：** Ryzen 5700X / RTX 4060 Ti
- **系统内存：** 16 GB

## 结论

当前固定编辑器镜头的持续低帧率主要受编辑器 CPU 链路限制。CPU 跟踪进一步定位到 Mass 编辑器子系统的 PrePhysics 处理阶段，其中 TEDS 的“Resolve hierarchy rows”层级解析任务占据主要时间，主线程等待这些任务完成。另一个独立、已确认的瓶颈是保存/进入 PIE 前的全场 ISM 同步，最近一次无变化同步仍耗时 135 秒。VSM 非 Nanite 队列溢出是已发生的 GPU 容量/复杂度风险，但当前镜头并非 GPU 主导。

## 一、当前实测基准与范围

采样为当前玻璃连廊前固定编辑器镜头，Epic 质量；未调整相机、光照、阴影、Lumen 或资产设置。采样时仅临时开启 GPU CSV 统计、取消后台 CPU 节流，采样后已恢复两项设置。MaxFPS=0、VSync=0；RayTracing、Lumen HWRT、VSM、Nanite 均开启。ScreenPercentage=0 表示使用编辑器默认解析规则，不能解释为 0% 或擅自视为 100%；本结果未验证固定 1080p 内部渲染分辨率。

完整受控样本为 360 帧、约 14.02 秒；统计首尾各排除 10 帧，保留内部所有异常，共 340 帧。全部原始帧都有实际场景 GPU 绘制。

## 二、优先级 P0：编辑器 TEDS 层级解析 / Mass 完成等待

CPU trace 的受控运行区间 24368–24380 秒内，UMassEntityEditorSubsystem::Tick 约 309 次，包含时间合计 9.091 秒，平均 29.42 ms，中位约 28.91 ms。PrePhysics 包含时间平均 29.11 ms。各线程“Resolve hierarchy rows”合计 8.892 秒，约占该 12 秒观察区间的 74%；这是多个线程 scope 的统计，最终以任务与等待的时间关联解释，不把所有 scope 机械相加为整帧。

独立逐帧核验确认：309/309 个主线程 Mass Tick 内都存在 resolver worker；其祖先均为 ExecuteForegroundTask → Mass Processor Worker Task → Resolve hierarchy rows。对并行 resolver 区间取并集后，覆盖主线程 Mass 时间包络的 97.74%，约 28.86 ms/帧。因此热点与主线程等待同帧对应，不能仅解释为一个无关的后台统计。

事件导出可能保留跨窗口边界的完整 scope；正式总耗时使用窗口裁剪后的统计。完全位于该窗口内的 307 帧，整帧均值 38.97 ms、中位 38.51 ms；Mass 中位 28.99 ms、等待中位 28.09 ms。

引擎源码确认编辑器 Mass 持续 Tick，串行派发各阶段并等待最后的 CompletionEvent；TEDS 在 PrePhysics 注册“Resolve hierarchy rows”处理器。未找到父行时，未解析状态会继续保留。动态层级实现还有在 chunk 内逐行查找行索引的操作。

当前 TEDS.Enable=true。该变量被源码标记为只读、启动阶段设置；不能在运行中把敲控制台关闭它当成可用方案。

已确认的是热点链路。尚未实测具体哪个 hierarchy、哪些父行持续未解析，也没有通过关闭 TEDS 的 A/B 测试证明可获得固定多少 FPS；不据此直接宣称引擎缺陷或所有 29 ms 均可完全移除。

**建议方案：**

1. 优先审计热点 query 的行数、父映射查找失败率、动态层级类型，以及其与场景原件/文件夹/组件数量的关系。

2. 在隔离的启动配置中做 TEDS/相关编辑器集成开—关—开对照，同时验证大纲、选中、撤销及工具兼容性；不直接卸载通用 Mass/StateTree 功能。

3. 若需源码优化，围绕父行映射变化增量处理、缓存已解析结果、避免失败行每帧全量重试、减少重复 chunk 内行索引查找。需要依赖状态变化触发重试，保留父子关系正确性。

4. 场景编辑侧按建筑/楼层分区加载或只加载当前编辑区域，保留可编辑原件与已有运行时实例的对应关系，降低同时参与编辑器层级维护的对象规模。

**验收：** 相同相机/像素数/质量复采 CPU+GPU，检查层级解析和主线程 P95 是否下降，并执行目录组织、选择、撤销回归；另测 Standalone/打包运行以区分编辑器专属成本。

## 三、优先级 P1：保存 / 进入 PIE 全场 ISM 同步

当前日志记录 138,620 Actor、9,408 组、104,614 自动实例；全部 9,408 组 unchanged、0 created，仍耗时 135.11 秒，其中 scan 115.061 秒。scan 内候选与材质 36.008 秒、分组及报告 62.890 秒、引用审计 16.062 秒。随后 staging 8.304 秒、commit 3.251 秒、验证 8.491 秒。

同次 PIE 总启动为 157.99 秒，关卡复制本身约 16.36 秒。Content/Python/init_unreal.py 自动安装同步钩子，campus_editable_ism.py 的 pre_save / begin_pie 无条件进入完整 sync 路径。

这是启动和保存等待的证据，不作为当前每帧 TEDS 时间的直接解释。本轮没有重新启动 PIE 或保存关卡，以免触发自动同步写入。

**建议方案：** 追踪变更 Actor/组并做增量同步；以稳定签名缓存材质、网格、变换及引用检查结果；无变化时快速返回；完整扫描保留为显式校验/恢复操作；将完整报告构造移到必要时执行。导入、删除、重命名、撤销、材质替换必须正确使缓存失效。

**验收：** 分别测完全无变化保存/进入 PIE、修改单个 Actor、修改多个组、撤销及引用变化；逐组验证实例数量/变换/材质一致性，不能用跳过校验换取短启动时间。

## 四、优先级 P2：VSM / 大范围几何 / 新植被

本次当前日志确有两次“非 Nanite 标记工作队列溢出”，与大量非 Nanite 网格覆盖阴影大范围有关。当前 IncludeInCoarsePages=1。

当前镜头 GPU 分项均值：Basepass 2.24 ms、Prepass 1.91 ms、ShadowDepths 1.41 ms、LumenSceneUpdate 0.92 ms（P95 3.40 ms，最大 7.21 ms）。LumenSceneUpdate 只是一个分项，不能当作全部 GI 成本；异步计算开启时各 GPU pass 不可简单相加。

9/27 别的编辑器镜头关闭阴影仅降低 GPU 中位约 2.14 ms、整帧均值约 1.34 ms，作为历史参考；没有把该差值当作当前镜头的收益。

当前需要分区 A/B 的候选：

- 远景森林：15,000 个树冠实例，45 个已有 ISM 组件，3 种网格均非 Nanite、单 LOD、投影且没有距离裁剪。

- 圆庭铺装：41,170 个 Cube 实例，8 个已有 ISM 组件，投影且没有距离裁剪。

- 新增椰树/食堂两种树/三种绿萝：264 个实例、9 个已有 ISM 组件，均非 Nanite、单 LOD、投影、无距离裁剪；当前 LOD0 三角按实例展开约 482 万。这只是资产复杂度，不是本镜头实际每帧提交三角。

    椰树：131,848 三角 ×17；榉树：69,824×7；樟树：85,404×9。

    绿萝 Runner/Drape/Column：6,348×157、2,920×56、8,772×18。

**建议方案：** 先按区域和可见距离确定 GPU 时间影响，再做远景代理/完整 LOD、空间分块与距离裁剪、适合资产的 Nanite、细小物体的远距阴影预算。现有区域已经实例化，不能把再次合批当成主要措施。将 Non-Nanite coarse-page inclusion 作为单独受控实验，并检查体积雾、透明材质的阴影需求；不把增大阴影缓冲容量作为默认根治手段。只有确认实际材质有 WPO/风动后才评估远距停用其变形和缓存失效。

**验收：** 森林边缘、圆庭、椰树庭院、礼堂后方、食堂庭院、木庭院各取固定镜头和行走路线，记录 GPU P95、Draw Calls、VSM 无效页/溢出与显存，同时检查远景过渡、阴影及室内外间接光外观。

## 五、优先级 P3：冷启动 PSO / 导航碰撞 / 内存

日志记录 50 次 PSO 创建 hitch（15 graphics、35 compute），0 precached；需在目标运行版本验证预缓存覆盖率与首条路线预热，并分开冷启动和热运行。该累计日志不意味着本次短采样中的每个长帧都由 PSO 造成。

导航导出发现两个高复杂度碰撞，分别约 259,200 和 201,376 三角。方案为简化可行走面碰撞、排除非可行走装饰的导航贡献、限制实际导航生成区域；需测生成时序再判断对运行帧时的影响。

本次显存中位约 6,894 MiB，相对 15,341 MiB 预算未逼近上限；系统可用 RAM 约 2.1 GB，存在余量较小的线索，但没有把缺页/内存溢出认定为当前主因。纹理池为 1,000 MB，日志未证实超预算，不建议没有证据就加大池。后续测内存、流送与 OS 缺页时间关联。

## 六、场景规模与已完成优化的边界

当前关卡有 138,620 编辑器 Actor，其中 122,976 是 StaticMeshActor。104,642 Actor 为 editor-only 原件；运行时自动 ISM 批次 9,408 个，在编辑器临时隐藏、运行时显示。统计已分开编辑器/运行时可渲染候选：约 327,891 / 327,862 个网格实例；该数量未扣除视锥、遮挡、流送和距离剔除，不能当作当前镜头实际绘制数。

约 255,065 个运行时非 Nanite 投影候选同样不是每帧实际投影数。

9/20 体育馆道路植物 Lumen Surface Cache 的 200–400 ms 尖峰已有后续修复并保存。当前 11 种 OPT 植物仍启用 Nanite，已扩展到 12,911 实例；本方案不把旧尖峰写成当前已复现问题，也不建议重复实例化已优化区域。

## 七、实施顺序与验收口径

先处理编辑器 TEDS 热点与启动/保存增量同步，再按路线处理 GPU 几何和阴影预算，最后补冷启动与内存/导航专项。每一步独立做 A/B，并验证编辑和画面功能。

若采用 60 FPS 目标，CPU/GPU 持续帧预算都需要约 16.67 ms；该目标尚未由用户指定，本次也未验证打包版本。不能直接用编辑器数值承诺最终游戏帧率。
